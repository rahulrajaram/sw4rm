# SW4RM Extension Release: v0.6.0

**Spec Version:** 0.6.0 (2026-02-15)

This file captures the protocol extension changes that shipped with spec version 0.6.0 and lists proposed enhancements under consideration.

## Extension Changes in v0.6.0

### SW4-004: Inter-Swarm Composition (0.2.1 -> 0.3.0)

New additions since v0.5.0:

- **Implementation profile (§9.4)**: Cross-SDK required behavior for cancellation
  cascade/grace handling, deterministic redirect target normalization, redirect
  loop detection, default redirect bounds, budget monotonicity enforcement, and
  spillover-disabled overload fallback.

- **Conformance test outline (§10)**: Normative test scenarios T-001 through
  T-018 covering depth limits, budget monotonicity, overload signaling, retry
  jitter, cancellation cascade, forced termination, gateway-only addressing,
  parent correlation, redirect loops, default redirect bounds, redirect
  budget/deadline monotonicity, grace clamp, spillover-disabled fallback, and
  canonical redirect target normalization.

- **Tightened cancellation semantics**: Grace period clamping to remaining parent
  grace time with 5000ms minimum floor (§5.2, §9.4).

### SW4-005: Spillover Routing (0.2.1 -> 0.3.0)

New additions since v0.5.0:

- **Implementation profile alignment (§15)**: SW4-004/SW4-005 interoperable
  profile requiring redirect target normalization, loop detection, default
  redirect bounds, budget monotonicity, cancellation cascade semantics, and
  spillover disable semantics.

- **Conformance test outline (§11)**: Normative test scenarios R-001 through
  R-013 covering spillover-disabled behavior, redirect signaling shape, health
  filtering, round-robin fairness, budget deduction, deadline enforcement,
  metadata continuity, backward compatibility, and redirect target
  canonicalization.

- **Tightened adaptive spillover**: Canonical redirect target normalization
  (gateways emit canonical registry `agent_id`; callers trim/resolve),
  cooldown/liveness filtering for recently-overloaded peers, and unresolved
  canonicalization treated as terminal validation failure.

## Proposed Enhancements

The following enhancements are candidates for this or future spec versions.
They were previously tracked in `spec_enhancements.md` (now absorbed here).

### 1. Explicit Request/Response Semantics

Add a standard response linkage field (`in_response_to`, `response_for_idempotency_token`)
and a `response_required` flag or `ResponsePolicy` sub-structure with timeout, retry
policy, and max attempts. When `response_required=true`, the sender transitions to
WAITING and the Scheduler tracks a pending response entry.

### 2. WAITING State Guidance for Responses

Define normative WAITING behavior for request round-trips: agents MUST enter WAITING
and preserve task assignment, WAITING MUST be bounded by `response_timeout_ms`,
and deployments without HITL MUST define a fallback on timeout.

### 3. Response Message Type

Add a canonical response payload schema containing `in_response_to`, `status`,
`payload`, `error_code`, and `note`. Clarify whether responses use
`message_type=DATA` with required `in_response_to` or a new `message_type=RESPONSE`.

### 4. Message Authorization (Agent Scope)

Explicitly state: "Any Agent MAY emit messages and handoffs subject to
Scheduler-enforced ACLs and policy." This avoids tool-specific constraints not
part of protocol intent.

### 5. Idempotency Token Guidance for Responses

Define response idempotency rules: responses carry a deterministic idempotency
token derived from the request token and response type; duplicates are
deduplicated by the Scheduler.

### 6. Activity Buffer Interaction with WAITING

When an Agent enters WAITING due to `response_required`, it MUST update its
Activity Buffer entry with a `waiting_on` field (message_id or correlation_id)
and a timestamp for auditability and operator visibility.

### 7. Backpressure + Response Required

If a response-required message is rejected due to `BUFFER_FULL`, the sender
MUST NOT enter WAITING; it MUST receive a NACK with `error_code=BUFFER_FULL`
and decide whether to retry or fail.

### 8. Handoff Context Content-Type

Require `context_snapshot_content_type` (application/json, application/protobuf,
text/plain) and enforce modality compatibility with target Agent.
